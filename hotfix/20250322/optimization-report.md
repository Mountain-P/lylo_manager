# Lylo Manager 流程與操作優化報告

> 報告日期：2026-03-22
> 範圍：畫面、操作流程、業務邏輯、使用體驗

---

## 一、盤點流程優化

### 1.1 掃碼盤點流程斷裂

**現狀問題**：
- 掃碼頁面 (`Inventory/Scan.vue`) 掃到多規格商品時，彈出 variation 選擇視窗讓使用者手動挑選規格。但實際場景中，條碼本身就應該對應到「特定規格」，不應該再讓使用者選。
- 根本原因：`routes/products.js:74` 的 barcode 搜尋同時查 `barcode` 欄位和 `wooId`，當查到的是 variable（母商品）而非 variation（子規格）時，才會觸發選擇視窗。

**建議**：
- 條碼應直接綁定到 variation 層級，而非 variable 層級
- 若掃到的是 variable 商品，應提示「此條碼對應的是母商品，請掃描子規格條碼」而非讓使用者從列表中選
- 在商品管理中加入「批次綁定條碼」功能，讓每個 variation 都有獨立條碼

### 1.2 快速盤點模式太簡陋

**現狀問題**：
- 快速盤點模式 (`Scan.vue`) 固定數量為 1，掃一次記一次
- 但實際盤點情境是：倉庫裡某商品有 50 件，員工不會掃 50 次

**建議**：
- 快速模式改為「掃碼後彈出數量輸入框，預填 1，按 Enter 即確認」，而非完全跳過數量輸入
- 加入「累加模式」：同一商品重複掃碼時，自動把數量 +1 而非建立新紀錄
- 掃碼頁面顯示「本次盤點清單」，列出已掃過的商品和累計數量，允許修改

### 1.3 盤點結果沒有確認流程

**現狀問題**：
- 員工盤點後數字直接寫入，沒有主管覆核機制
- `InventoryLog` 沒有 review/approval 狀態欄位
- 若員工盤錯數字，只能由 boss 刪除紀錄後重新盤點

**建議**：
- 加入盤點覆核流程：員工提交 → 主管確認 → 正式生效
- 在 `InventoryLog` 加入 `status` 欄位（pending / approved / rejected）
- 異常盤點（diffQty 大於門檻值）自動標記為待覆核
- 主管可在 Dashboard 或獨立頁面看到待覆核清單

### 1.4 盤點沒有「任務」概念

**現狀問題**：
- 系統沒有「盤點任務」的概念，無法追蹤「這次盤點從什麼時候開始、到什麼時候結束、由誰負責哪些區域」
- Dashboard 只顯示「已盤 / 未盤」比例，但無法區分是哪一輪盤點

**建議**：
- 加入「盤點任務」功能：
  - 主管建立任務（指定日期、負責人、商品範圍）
  - 員工在任務內進行盤點
  - 任務完成後可產生報表
  - 歷史任務可回顧比較
- 這能解決目前 `countedQty` 會被覆蓋、無法追溯多次盤點紀錄的問題

### 1.5 重複掃碼的邏輯不合理

**現狀問題**：
- `Scan.vue` 的重複偵測是「2 秒內同一條碼視為重複」
- 但如果員工真的要修正剛才的數量，2 秒後再掃就會建立第二筆紀錄

**建議**：
- 改為「同一盤點 session 中，同商品只保留最新一筆紀錄」
- 或加入「已掃過此商品，是否要更新數量？」的確認提示

## 二、商品管理流程優化

### 2.1 商品列表的 variation 展開體驗差

**現狀問題**：
- `Products/Index.vue` 點擊展開 variable 商品時，每次都重新呼叫 API 載入 variations
- 展開後的子表格和主表格樣式不一致，不容易對照
- 多規格商品的彙總邏輯有問題：母商品顯示的 `countedQty` 是所有 variation 的加總，但可能只有 1/5 的規格被盤過，使用者看到數字會以為全部盤完了

**建議**：
- 展開過的 variations 快取起來，不要每次都重新載入
- 母商品增加顯示「已盤規格數 / 總規格數」（例如 `2/5 已盤`）
- 未盤的 variation 高亮標示，引導員工完成

### 2.2 商品搜尋邏輯混亂

**現狀問題**：
- `routes/products.js:58-109` 的搜尋邏輯有三種模式（barcode / SKU / 文字），但前端只有一個搜尋框
- 輸入純數字被當作 barcode 搜尋，但 SKU 也可能是純數字
- barcode 搜尋同時查 `barcode` 和 `wooId` 兩個欄位，可能找到錯誤的商品

**建議**：
- 前端搜尋框加上類型切換（全部 / 名稱 / SKU / 條碼）
- 或改用更智慧的搜尋：先精確比對 SKU 和 barcode，再模糊比對名稱
- barcode 搜尋結果如果有多個匹配，應讓使用者選擇而非自動取第一個

### 2.3 商品詳情頁缺少操作入口

**現狀問題**：
- `Products/Detail.vue` 只能「看」，不能直接操作
- 要盤點這個商品必須返回列表頁找到它再點盤點按鈕

**建議**：
- 詳情頁加入「立即盤點」按鈕
- 加入「編輯商品」快捷入口（boss 角色）
- 加入「查看 WooCommerce 訂單」連結

### 2.4 缺少批次操作

**現狀問題**：
- 商品列表不支援多選 + 批次操作
- 要盤點多個商品只能逐個點擊

**建議**：
- 加入 checkbox 多選功能
- 支援批次盤點（選取多個商品 → 依序輸入數量）
- 支援批次匯出選取商品的資料

## 三、銷售排行與預購統計優化

### 3.1 銷售排行查詢太慢

**現狀問題**：
- `Products/SalesRanking.vue` 查詢需要 30-60 秒，期間使用者只能等待
- 原因是 `routes/products.js:587-615` 會對每個訂單狀態分別呼叫 WooCommerce API，逐頁抓回所有訂單後在記憶體中彙總

**建議**：
- 加入查詢進度條（目前只有 loading spinner，沒有進度資訊）
- 第一次查詢後快取結果，短時間內重複查詢直接回傳快取
- 將銷售統計改為排程計算（例如每小時更新一次），前端直接讀取計算好的結果
- 或至少顯示「正在從 WooCommerce 抓取第 3/8 頁訂單...」的進度提示

### 3.2 銷售排行與庫存斷開

**現狀問題**：
- 銷售排行頁能看到每個商品的銷量和當前庫存
- 但看完之後沒有下一步動作——看到庫存不足的商品，無法直接建立採購需求

**建議**：
- 銷售排行加入「需補貨」標記（銷量高但庫存低的商品）
- 加入「一鍵加入補貨清單」功能
- 或至少在商品 modal 中提供「更新在途量 (onOrderQty)」的入口

### 3.3 預購統計排除邏輯不直覺

**現狀問題**：
- `Orders/PreOrderStats.vue` 的排除條件用「分類排除」和「商品名稱關鍵字排除」
- 使用者要手動輸入要排除的關鍵字，用逗號分隔
- 預購商品的判斷條件寫死在程式碼中：`attribute.name === '貨況' && option === 'pre-order'`

**建議**：
- 排除條件改為更直覺的 UI：顯示所有分類的 checkbox，讓使用者勾選要「包含」的（而非排除）
- 關鍵字排除改為 tag input 元件，輸入一個按 Enter 加入一個
- 預購判斷條件改為可設定的，不要寫死在程式碼中

## 四、WooCommerce 同步流程優化

### 4.1 同步狀態回饋不足

**現狀問題**：
- `Sync/Index.vue` 在手動觸發同步後，頁面每 3 秒 polling 一次狀態
- 但如果使用者離開這個頁面再回來，polling 不會自動啟動（只在 mount 時判斷）
- 同步失敗時只顯示「同步失敗」，沒有告訴使用者是哪些商品失敗、為什麼失敗

**建議**：
- 使用全域的同步狀態指示器（放在 MainLayout 的 header 上），不管在哪個頁面都能看到同步進度
- 同步完成後顯示摘要通知：「同步完成：新增 5 個商品、更新 120 個庫存、3 個錯誤」
- 錯誤記錄可點開查看具體失敗原因和商品名稱

### 4.2 同步與盤點的衝突未處理

**現狀問題**：
- WooCommerce 同步會更新 `stockQty`（系統庫存）
- 盤點更新的是 `countedQty`（實際盤到的數量）
- 但 `expectedQty` 的更新時機不明確——它應該是什麼時候設定的？由誰設定的？
- 如果同步途中有人在盤點，可能會出現資料不一致

**建議**：
- 明確定義 `expectedQty`、`stockQty`、`countedQty`、`salesQty` 四個欄位的業務含義，在 UI 上用清楚的標籤解釋
- 同步進行中暫停盤點功能（或至少提示使用者「同步中，盤點結果可能不準確」）
- 在商品詳情頁加入欄位說明 tooltip

### 4.3 同步設定太隱蔽

**現狀問題**：
- 同步設定藏在 dialog 裡，使用者不容易發現可以調整同步間隔、批次大小等
- 設定項目的說明不足（例如 batch size 10-500 代表什麼意義？）

**建議**：
- 同步設定改為獨立區塊直接顯示在頁面上，不需要點開 dialog
- 每個設定項加上簡短說明文字
- 加入「同步範圍」設定：可以只同步特定分類的商品

## 五、使用者管理與權限優化

### 5.1 員工角色功能太少

**現狀問題**：
- Employee 角色登入後只能看到「預購統計」和「個人資料」兩個頁面
- 員工的主要工作（盤點）反而需要 boss 權限才能進入商品列表和掃碼頁面
- 這和實際使用場景矛盾——盤點應該是員工的日常工作

**建議**：
- 重新設計權限架構：
  - **員工可用**：掃碼盤點、商品列表（唯讀）、盤點記錄（自己的）、預購統計、個人資料
  - **主管專用**：商品編輯/刪除、使用者管理、WooCommerce 同步設定、報表匯出、盤點記錄刪除
- 目前的路由守衛 (`router/index.js`) 用 `requiresBoss: true` 控制，需要改為更細緻的權限設計

### 5.2 員工活動追蹤不夠即時

**現狀問題**：
- 主管要看員工的盤點情況，要進入「使用者管理 → 點員工 → 查看詳情」
- 詳情中顯示的是彙總數字（今日/本週/本月），看不到即時的盤點動態

**建議**：
- Dashboard 加入「即時盤點動態」區塊，顯示最近 10 筆盤點紀錄（含員工名稱）
- 或加入「盤點看板」頁面：以時間軸方式顯示所有員工的盤點進度

### 5.3 密碼重設流程不安全

**現狀問題**：
- `routes/users.js` 有兩個密碼重設端點：`/change-password`（設任意密碼）和 `/reset-password`（重設為 `password123`）
- 重設密碼後沒有通知該員工，員工不知道密碼被改了
- 沒有強制「首次登入修改密碼」的機制

**建議**：
- 合併為一個端點，產生隨機臨時密碼
- 重設後標記使用者為「須變更密碼」狀態
- 下次登入時強制導向修改密碼頁面

## 六、Dashboard 優化

### 6.1 Dashboard 資訊密度不足

**現狀問題**：
- Dashboard 只有 4 個統計數字 + 最近 5 筆活動 + 同步狀態
- 作為主管的主要工作台面，缺少關鍵決策資訊

**建議**：
- 加入以下區塊：
  - **庫存警告**：庫存為 0 或低於安全庫存的商品清單
  - **盤點異常 Top 5**：差異最大的商品，可直接點擊處理
  - **今日員工盤點排行**：誰盤了多少、進度如何
  - **近期銷售趨勢**：簡易折線圖顯示近 7 天銷量
  - **待處理事項**：待覆核的盤點、同步錯誤等

### 6.2 快捷操作不夠快

**現狀問題**：
- Dashboard 的快捷操作（掃碼盤點、商品列表、同步）只是導航連結
- 最常用的操作應該能直接在 Dashboard 完成

**建議**：
- 加入「快速搜尋」：在 Dashboard 頂部放一個搜尋框，輸入商品名/SKU/條碼直接跳到該商品
- 統計卡片點擊後直接在 Dashboard 下方展開篩選後的商品列表，不用跳頁

## 七、整體 UX 改善

### 7.1 缺少操作確認與撤銷

**現狀問題**：
- 盤點提交後無法撤銷，只能由 boss 刪除紀錄
- 刪除操作有確認 dialog，但盤點提交（同樣是重要操作）卻沒有

**建議**：
- 盤點提交後 5 秒內可撤銷（類似 Gmail 的撤銷發送）
- 或在提交前顯示確認摘要：「商品：XX、數量：50、系統庫存：48、差異：-2，確定提交？」

### 7.2 頁面之間導航不夠流暢

**現狀問題**：
- 從盤點記錄頁想查看某商品詳情，點擊後跳到商品詳情頁，但沒有「返回盤點記錄」的按鈕
- 使用者只能按瀏覽器返回鍵或重新點側邊欄
- 商品詳情頁的「返回」按鈕用的是 `router.back()`，如果是直接 URL 進入就無法返回

**建議**：
- 所有頁面加入麵包屑導航（Breadcrumb）
- 「返回」按鈕改為導向固定頁面（如商品列表），而非 `router.back()`

### 7.3 篩選條件不持久

**現狀問題**：
- 商品列表的篩選條件在離開頁面後會消失
- 使用者設好篩選 → 點進某商品 → 返回列表 → 篩選條件全部重設

**建議**：
- 將篩選條件存入 URL query params 或 store
- 返回頁面時自動還原篩選狀態

### 7.4 表格操作按鈕太擠

**現狀問題**：
- 商品列表和記錄列表的每行操作按鈕都擠在一起（盤點、查看、展開等）
- 手機上幾乎無法精確點擊

**建議**：
- 手機端改為滑動操作或長按彈出選單
- 或將操作收進「更多」下拉選單中

### 7.5 缺少數據匯入功能

**現狀問題**：
- 系統只有匯出（CSV export），沒有匯入
- 主管無法用 Excel 批次更新商品資料或匯入盤點結果

**建議**：
- 加入 CSV 匯入功能：
  - 匯入商品資料（更新名稱、SKU、條碼、expectedQty）
  - 匯入盤點結果（批次盤點後上傳）
  - 匯入前預覽變更、確認後寫入

### 7.6 手機端體驗待加強

**現狀問題**：
- 掃碼盤點是手機端的核心使用場景
- 但目前掃碼頁面佈局是 8:4 分欄，手機上相機預覽區太小
- 統計和設定卡片在手機上佔據太多空間

**建議**：
- 手機端掃碼頁面全螢幕顯示相機預覽
- 統計和設定收進可摺疊面板
- 掃碼結果以底部浮動 sheet 顯示，不離開掃碼畫面

## 八、業務邏輯問題

### 8.1 庫存四個數量欄位語意不清

**現狀問題**：
系統有四個關鍵數量欄位，但它們的關係和更新時機不夠明確：
- `expectedQty`：期望庫存量（何時設定？由誰設定？）
- `stockQty`：WooCommerce 同步過來的庫存量
- `countedQty`：盤點數量（每次盤點覆蓋前次？還是累加？）
- `salesQty`：銷售量（從 WooCommerce 同步？還是手動設定？）

差異計算公式：`diffQty = expectedQty - (countedQty + salesQty)`

這個公式假設 `countedQty + salesQty` 應等於 `expectedQty`，但語意上不太合理——「盤到的 + 賣掉的 = 期望的」？如果是進貨 100 件、賣了 20 件、盤點時應該剩 80 件。

**建議**：
- 簡化為更直覺的模型：
  - `systemStock`：系統計算的庫存（= WooCommerce 同步值）
  - `countedStock`：實際盤點數量
  - `difference`：差異（= countedStock - systemStock）
- 在 UI 上清楚標示每個數字的含義和更新來源

### 8.2 盤點紀錄覆蓋問題

**現狀問題**：
- 每次盤點會更新 Product 的 `countedQty`，直接覆蓋上次的值
- 如果有多次盤點，只能從 InventoryLog 查看歷史
- 但商品列表顯示的 `countedQty` 只是最後一次的值

**建議**：
- 盤點結果應該和「盤點任務」綁定
- Product 上的 `countedQty` 應標示是哪次盤點的結果、何時盤的
- 或改為只從最近一次有效的 InventoryLog 讀取，不存在 Product 上

### 8.3 「異常」判定過於簡單

**現狀問題**：
- 只要 `diffQty !== 0` 就標記為異常
- 但實際業務中，小差異（1-2 件）可能是正常損耗

**建議**：
- 加入「容許誤差」設定（例如差異在 ±2 件或 ±5% 以內視為正常）
- 異常分級：輕微異常（黃色）/ 嚴重異常（紅色）
- 異常需要填寫原因才能結案（目前只有 `note` 自由文字欄位）

## 九、建議優先順序

### 立即改善（影響最大、改動最小）
1. 員工權限開放盤點和商品瀏覽功能
2. 篩選條件持久化（存入 URL 或 store）
3. 母商品顯示「已盤規格數 / 總規格數」
4. 商品詳情頁加入「立即盤點」按鈕
5. 同步狀態放到全域 header
